2. PRODUCT THESIS & CORE LOOP
================================================================================
Loop: discover/post → shortlist in a private Circle → vote (can/maybe/cannot) in
a Decision Room before a hard deadline → finalize one plan → each person confirms
independently → find a buddy → attend → vouch for people who were great → repeat.

Honesty rules (never violate, in code or copy):
- Availability is NOT a commitment. A confirmed plan is NOT a ticket. Registration
  always happens on the organizer's own site; opening a source link never
  registers anyone. Attendance is self-reported, never verified check-in.
- Unknown price is shown as "Price unknown — check source", never inferred free.
- Every listing carries its source URL. The recommendation formula is published
  in the UI, never a black box.
- No invented users, testimonials, counts or endorsements anywhere. Demo data is
  fictional, labeled "DEMO DATA", and excluded from any real claims.
- No dark patterns: no streak shame, no countdown pressure, no XP for invites,
  no XP for vouches, no paid safety/privacy ever.
- Target users: students 18+, professionals, job seekers, people between roles,
  founders, community organizers. India-first (Bengaluru demo context, INR,
  Asia/Kolkata) but timezone/currency-generic in the data model.

5. BUSINESS RULES (all pure functions in packages/core/src/rules.ts — TESTED)
================================================================================
XP (XP_RULES): checkin 1 · vote 5 · event_posted 10 · connection 10 (max 2 per
  week per user, once per unordered pair EVER via canAwardConnection) ·
  plan_confirm 15 · buddy 10 · referral 75 (both sides).
  DAILY_CONTRIBUTION_CAP = 30/day over capped actions
  {vote, event_posted, connection, plan_confirm, buddy}.
  Referral, checkin and vouches are OUTSIDE the cap. Vouches award NO XP —
  reputation must never be farmable.
  awardXp(ledger, action, key) is dedupe-keyed: same key never pays twice.

Levels: 0 Explorer · 100 Connector · 250 Planner · 500 Constellation.
  Accent themes (coral/sage/saffron) unlock at 250 XP — cobalt always free.
  Founding members (user.founding) bypass the 250 gate.

Badges (BADGES map): founding, first_plan, connector, vote_starter,
  helpful_intro, curator (≥2 people plan to attend your event), crew_buddy.

Streaks (applyCheckin): one intentional check-in per account-local day
  (dayKeyInTz with user.timezone). Same-day repeat = no-op. Gap of 1 day
  continues. Gap of 2 days consumes ONE grace credit from the MISSED day's
  week (rewardWeekKey runs Monday-start) if not already used that week —
  streak preserved, no XP for the grace day. Gap ≥ 3 resets count to 1.
  rewardWeekKey(UTC, Sunday) belongs to the previous Monday.

Decision scoring (scoreDecision): score = 100 × (0.65·can + 0.15·maybe +
  0.20·favorite) / eligibleVoters.length (the snapshot roster, NOT current
  members). Quorum: responded ≥ ceil(60% × N) AND N ≥ 2. Ties stay ties (no
  top). All-zero preference = no recommendation. Blank responses are NO
  RESPONSE, never 'cannot'. Warnings surface: tie, no-preference, quorum miss,
  roster changes, non-responders. FORMULA_VERSION string is shown in UI.

Decision lifecycle: open → (deadline passes, sweep() flips) closed →
  finalized (owner only; needs a winner OR a written overrideReason; result
  snapshot created; ONE plan created, status 'awaiting'). Plan → 'confirmed'
  when ≥ 2 eligible participants independently confirm (owner confirms
  separately). Material event edits (title/time/status) flip live plans to
  'review_needed' (canceled event → plan 'canceled') and notify everyone.
  Past event end + noncanceled → 'completed' via sweep(). Confirmations are
  per-person; never implied by voting.

Peer vouches (TRUST_WINDOW_DAYS = 14): requires BOTH users to have a
  participation record (RSVP or plan confirmation) on the same event AND that
  event's startUtc ≤ now. No self-vouch, blocked pairs rejected, ONE vouch per
  (from,to) per rolling window (hasActiveVouch). computeTrust() counts only
  vouches newer than 14 days: hearts, per-claim verification counts, polite/
  professional counts. Public surfaces show positive signals only; concerns go
  through reports; vouch.note is moderator-only.

Referrals: signup with ?ref=CODE → both sides +75 XP (dedupe key `ref:<invitee>`,
  once per invitee forever), referrer +14-day boost (directory sort), invitee
  +7-day welcome boost, Connector badges. If referrer isFounderTeam → invitee
  becomes FOUNDING (user.founding=true, badge 'founding', +100 XP welcome,
  all accents, directory priority).

Roles (SiteRole): 'founder' (exactly one, immutable, cannot be suspended via
  console) → 'cofounder' (MAX_COFOUNDERS = 2, appointed only by founder) →
  'moderator' → 'member'. isStaff() = founder|cofounder|moderator (report
  resolution, event editing rights). isFounderTeam() = founder|cofounder
  (founder console, adminUpdateUser, adminSetRole, adminSetSuspended).
  canSetRole() encodes the matrix; adminSetRole() additionally enforces the
  cofounder cap. Every admin action appends to state.audit. Suspended users:
  login rejected, shell shows suspension screen, currentUserId cleared on suspend.

Team claim codes (client-side launch conveniences, in types.ts):
  FOUNDER_CLAIM_CODE   = 'CC-FOUNDER-2026'  → claims founder seat if vacant
  COFOUNDER_CLAIM_CODE = 'CC-CREW-2026'     → claims a cofounder seat if ≤2 taken
  Server-side invitations replace these at the backend milestone.

Blocking: user.blocked[] — gates connection requests, buddy requests to that
  person, and DMs (isBlocked checks BOTH directions). Blocking also declines
  any pending connection between the pair.

9. KEY FLOWS (step-by-step — an edit must not break these)
================================================================================
SIGNUP: Auth page → signup() validates → claim code check → user created
  (referral code generated) → founding/standard referral XP + boosts + badges →
  notifications + pulse → navigate('/app'). New users get city '' → dashboard
  nudges profile completion.

VOTE: Circle detail → New decision modal (pick 2–8 candidates from public +
  circle events, deadline ≥ +1h, optional live results) → Decision Room ballot:
  per-candidate can/maybe/cannot buttons (aria-pressed), optional favorite
  (only on can/maybe), clash warning + acknowledge checkbox when the candidate
  overlaps my RSVPs/confirmed plans → submit (deadline-checked; editing
  overwrites the ballot, XP once) → after deadline sweep() closes → owner sees
  Results (formula + counts + quorum + warnings) and Finalize panel (auto-pick
  top, or choose + override reason) → plan 'awaiting' → notifications → each
  eligible person Confirms/Declines (XP on confirm) → ≥2 confirmations flip to
  'confirmed' (+ pulse). Event edits/cancels flip live plans to review_needed.

VOUCH: Event page attendee row (event started + shared record + no active
  vouch) or profile page → VouchModal (pick shared event, hearts, claim
  checkboxes from the target's actual public values, conduct chips, private
  note) → vouchUser() gates → trust chips update everywhere (People cards show
  ⭐ founding first, then boost).

REFERRAL: Referrals page → copy link (#/auth?mode=signup&ref=CODE) or native
  share → friend signs up → both sides XP/boosts; founder-team link → founding.

ADMIN: Founder console = Live telemetry (adminStats via CountUp) + invite
  leaderboard (referralLeaderboard) + team invite links + pulse feed + accounts
  table (edit modal → adminUpdateUser; role buttons → adminSetRole; suspend →
  adminSetSuspended) + audit log. All actions audited.

EVENT EDIT: owner or staff → edit modal → updateEvent → material changes
  propagate to plans (review_needed) + RSVP notifications. Cancel event →
  plans canceled, participants notified.

16. WORKING CONVENTIONS FOR AI TOOLS (how to change this project safely)
================================================================================
Definition of done for ANY change:
  1) npm run typecheck (both workspaces clean)
  2) npm test (27+ passing)
  3) npm run build (clean)
  4) Browser-verify the affected journey on the built artifact
  5) Update PROJECT_STATUS.md (append), docs/ACCEPTANCE_MATRIX.md (new rows),
     and this file if rules/structure changed
Adding a feature (the recipe, docs/ARCHITECTURE.md):
  contract first (core/types) → policy second (core/rules + tests) → actions
  third (store.ts, gates in the action not the JSX) → UI last → evidence.
Style rules:
  - Strict TS, no `any` in new code, comment the WHY not the what.
  - Copy: warm, brief, honest. No fake data, no dark patterns, no emoji-only
    states. Match existing voice (see §2 and current pages).
  - New business rules MUST be pure functions in core with tests.
  - New storage fields: bump cc_state key + add backfill in load() (§7).
  - Privacy: every new user-facing field needs a privacy story (who sees it,
    where to hide it) wired into privacy toggles + publicView().
  - Windows/Git pitfalls: bash CWD locks directories (cd out before rm/mv of a
    dir); nested .git in dist blocks git mv; avoid sed patterns containing
    `||` (delimiter clash) — use Edit tools; apps/web/dist has a nested git
    repo used only for the deploy push.
  - Never push: founder prompt files (0*_*.txt), node_modules, dist to main.
